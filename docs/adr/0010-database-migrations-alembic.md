# ADR 0010: Database migrations with Alembic

## Status

Accepted

## Context

The program stack targets PostgreSQL with SQLAlchemy and Alembic. Phase 1 needed an explicit migration workflow before schema work accelerates in Phase 2.

## Decision

- Use **Alembic** as the sole migration tool for the FastAPI service (when the `backend/` application package exists).
- **One linear migration history** per environment family (`main` branch); no long-lived divergent migration branches.
- **Naming:** `YYYYMMDD_description` or Alembic autogenerate revision IDs with human-readable `message` in the revision docstring (pick one style in the first migration PR and keep it).
- **Autogenerate** is allowed for iteration in development; **review** autogenerated deltas before merge; production applies only reviewed revisions.

## Rationale

- Standard SQLAlchemy pairing; supports downgrade paths for rollback planning.
- Clear audit trail for schema tied to API releases.

## Alternatives considered

- **Raw SQL migration folders only:** Rejected — loses model sync and team ergonomics.
- **Prisma / other ORM:** Rejected — backend is Python-first per stack decision.

## Android-first timeline impact

Neutral: migrations land with backend vertical slice; decision prevents rework arguments later.

## Rollback / migration

Alembic `downgrade` supported where safe; destructive changes require expand/contract pattern documented in the migration PR.
